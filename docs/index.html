How I built a Jira product with nx-domainify

This is the walkthrough behind wizardnet972/jira. It is a Jira-style Angular app whose libraries were generated with nx-domainify, not hand-grown folders.

I am writing it the way I actually worked: product language first, generators second, fights with boundaries in the middle.

Why I am talking to you like this

Most Nx articles start at project.json. That is the wrong end of the stick for a domain-driven app.

If you start with folders, you will invent a shared domain, put half the product in it, and then spend a week arguing with ESLint. If you start with the product — what a project is, what an issue is, who owns a sprint — the libraries almost name themselves.

nx-domainify does not design the product for you. It only makes the design expensive to cheat.

I did not start with folders or generators

I did not open the monorepo and ask “what libs do I need?”

I asked what a delivery team actually does in Jira. They keep a project. They file issues against it. They arrange those issues on a board. They commit a slice of work to a sprint.

That is four conversations, not one “app module.” Only after those words were stable did I run a generator.

Strategic design: what is this product actually about?

This demo is not “a clone of Jira Cloud.” It is a thin delivery surface. You pick a project, see its board, create and move issues, then plan and report on a sprint.

Everything else is decoration. Search lives in the shell because people search from anywhere. Theme and sidebar collapse live in the shell because they are chrome, not product language.

If a screen did not change how work moves through a project, it did not become a domain.

Finding the language of the business

I kept the ubiquitous language small and boring on purpose. A project is the container: key, name, lead. An issue is the unit of work: key, type, status, priority, points, assignee. A board is the current view of issues in columns. A sprint is a time-boxed set of issues, with a state of future, active, or closed.

I refused words that sounded architectural. There is no “module,” “widget,” or “shared kernel domain” in the product language. Those are workspace words.

Drawing bounded contexts — and throwing some away

The first sketch had more contexts than the repo. I had users, search, notifications, workflow, reporting, and settings. Most of those collapsed.

Users are records the project lead and issue assignee point at. They do not have their own screens, so they are not a domain. Search is a query over issues, used by the shell. Workflow is todo → in-progress → in-review → done on an issue. Reporting is a sprint view. Settings is a project feature.

Throwing contexts away is the useful part of DDD. The leftover four still had to stand alone.

Why I kept four domains, not seven

project, issue, board, and sprint each have a reason to change. Project changes when the container changes: name, lead, list, create. Issue changes when work items change: create, detail, transition. Board changes when layout changes: columns, WIP, backlog. Sprint changes when the time-box changes: start, remaining days, velocity.

A fifth product domain would have been vanity. A “users” domain with no feature is a table, not a context. A “search” domain is a method on issues. A “workflow” domain is a status enum.

I later added shell for the application chrome: sidenav, theme, project switcher, layout outlet. Shell is not a Jira concept. It is the host. It may depend on shared UI and the shared data kernel. It may not import project, issue, board, or sprint.

Shared is not a fifth product domain

This was the rule I had to repeat the most: there is no shared domain.

Shared is only kits. The UI kit is button, avatar, badge, empty-state, icon, and card. The util kit is dates, format, id, query-params, and data.

@jira/util-data is the kernel: JiraStore, JiraClient, jiraKeys. It holds in-memory projects, issues, boards, sprints, and users. Every domain talks to that kernel. No domain talks to another domain.

The first time I let board import @jira/issue-ui-card, the isolation story was a lie. Board and sprint now render a dumb @jira/ui-card. Issue still owns issue-ui-card. Domain UI stays inside its domain.

How I mapped DDD onto nx-domainify tags

nx-domainify:init writes ESLint depConstraints. I used them as the architecture, not as decoration.

Type flows downhill. type:app may reach api, feature, ui, domain-logic, and util. type:feature and type:api may reach ui, domain-logic, and util. type:ui may reach domain-logic and util. type:domain-logic may reach domain-logic and util. type:util may only reach util.

Domain flows stay home. domain:shared may only reach domain:shared. domain:project may reach domain:project and domain:shared. Issue, board, sprint, and shell follow the same pattern.

Features cannot import type:api. Facades live in type:domain-logic and talk to infrastructure services, which talk to JiraClient.

I originally tagged domain UI as scope:shareable so board could reuse the issue card. That coupled the domains. I removed the tag and the constraint. Isolation is now the default, not an option.

Creating the Angular monorepo

The workspace is a normal Nx 23 Angular app. I started there, then used the plugin for every domain artifact. I did not use @nx/angular:library to place those libraries.

npx create-nx-workspace@latest jira --preset=angular-monorepo

Installing the plugin and running init

pnpm add -D nx-domainify
pnpm exec nx g nx-domainify:init

init does two things I actually used. It writes the DDD ESLint constraints. It also installs an agent skill at .cursor/skills/nx-domainify-generate, and the Claude copy. The skill is blunt: prefer nx-domainify:*, run --help when a flag is unknown, and do not mkdir library folders by hand.

That last line saved the repo. Every time I was tempted to “just create the folder,” the skill said no.

The first domain landed at the workspace root

The first nx-domainify:domain in a fresh workspace wants to land at the root. Pass --directory=libs on that first domain only. Later domains inherit libsDir.

pnpm exec nx g nx-domainify:domain project --directory=libs

I learned this by generating once in the wrong place and removing the project with @nx/workspace:remove. Do not delete library folders by hand and hope Nx forgets them.

Generating in order: domain, then everything else

Order is not style. The feature generator writes a facade into the domain library. The domain has to exist first.

I generated issue the way I generated the rest of the product. Domain first, then the screens, then the API if the context actually needed one.

pnpm exec nx g nx-domainify:domain issue
pnpm exec nx g nx-domainify:feature list --domain=issue
pnpm exec nx g nx-domainify:feature detail --domain=issue
pnpm exec nx g nx-domainify:feature create --domain=issue
pnpm exec nx g nx-domainify:api issues --domain=issue

UI and util omit --domain when they belong in shared.

pnpm exec nx g nx-domainify:ui button --directory=ui --skipPrefix
pnpm exec nx g nx-domainify:util data --directory=util --skipPrefix

Without --skipPrefix you get libs/shared/ui/ui-button. With it you get libs/shared/ui/button.

Project got list, create, and settings, plus a card, a header, and key/filters utils. Issue got list, detail, and create, plus the issues API, a card, a status, and key/priority utils. Board got view, configure, and backlog, plus a column and layout/wip utils. Sprint got active, planning, and report, plus a header, a burndown, and dates/velocity utils. Shell got layout, then appearance and workspace infrastructure.

UI libraries are empty on purpose

nx-domainify:ui creates the library, tags, and path. It does not create a component. That is correct. A UI kit should be a decision you make after the library exists, with @nx/angular:component --export.

I ran that second command for every visual: button, avatar, badge, empty-state, icon, card, plus the domain cards and headers.

Shared UI stays dumb. Inputs are strings and numbers. No Issue type, no facade, no query. If the card needs priorityLabel, that knowledge belongs in the issue domain, not in @jira/ui-card.

Filling the kernel: one store, many facades

JiraStore is an in-memory signal store. JiraClient is the async port: every method returns a Promise, even though the data is local. That let facades and infrastructure use TanStack Query as if a backend existed. jiraKeys is the query-key catalog. Mutations invalidate jiraKeys.all or a narrower key.

The first version put injectQuery and injectMutation in every facade. List and settings both listed projects. Active, planning, and report all listed sprints. That is the same service written three times.

I moved the shared query and write paths into domain infrastructure. ProjectsService feeds list, create, and settings. IssuesService feeds list, detail, and create. BoardService feeds view, backlog, and configure. SprintsService feeds active, planning, and report. WorkspaceService and AppearanceService feed the shell layout.

Facades still exist. They map data for one screen: filter projects, stack board columns, compute velocity. They do not own the HTTP-shaped port.

I do not use effect to hydrate forms. Settings uses linkedSignal so the fields follow the current project and the template can still call facade.name.set(...). Privates are #client, #queryClient, #store. Templates call signals directly. Methods stay for real work: save, move, plan, open, setWip, toggleTheme.

Why the only API sits on the issue domain

Features cannot import type:api. That is the constraint, and it is the point.

Issue is the only context that needed an explicit application API. IssuesApi is a named port over JiraClient. The other domains call JiraClient from their own infrastructure. That is enough for a demo.

I did not create ProjectsApi or SprintsApi just to make the diagram symmetric. An API library is for a boundary you intend to keep when the client is no longer in-memory. Issue is the one I would extract first.

Boundary fights I actually hit

The first domain landed at the root. --directory=libs once. Then I stopped thinking about it.

Board wanted the issue card. I let it, then undid it. Cross-domain UI is coupling with extra steps. Shared UI is the escape hatch, and it must stay dumb.

Shell wanted to be the app. I built the sidenav in apps/jira, and that made the app a feature. The app is now <router-outlet /> plus routes. The layout is @jira/shell-feature-layout. Routes load the shell as the parent and lazy-load domain features as children.

Search imported IssuesApi from the shell facade. Features and domain-logic cannot import type:api. Shell search now goes through JiraClient.searchIssues. The issue API stays inside the issue domain.

Facades grew effects and wrappers. effect to copy project fields into inputs was the wrong primitive. linkedSignal is the copy that stays in sync. Setters that only wrap signal.set were noise. The template already has the signal.

Composing screens without cheating

A feature class is boring on purpose.

export class View {
  facade = inject(ViewFacade);
}

The feature owns the template and the providers. The facade owns the screen model. The infrastructure service owns the queries.

The app does not compose screens. It composes routes.

{
  path: '',
  loadComponent: () => import('@jira/shell-feature-layout').then((m) => m.Layout),
  children: [
    { path: '', pathMatch: 'full', redirectTo: 'board' },
    ...projectRoutes,
    ...issueRoutes,
    ...boardRoutes,
    ...sprintRoutes,
  ],
}

If I needed an issue card on the board, I did not import the issue feature. I passed primitives into @jira/ui-card. That is composition without a domain import.

Making it look like Jira

Look is Tailwind v4 in the templates. Global tokens live in apps/jira/src/styles.css as --jira-* CSS variables, mapped in @theme. Dark mode is html.dark plus @custom-variant dark (&:where(.dark, .dark *));. A boot script in index.html applies the stored theme before paint.

I tried a navy slab sidebar, then a floating rounded card. The one that matched the product was a flush light rail: icon plus label, search in the sidebar, collapse control at the top, avatar at the bottom. Workspace and Projects are sections with chevrons that actually collapse.

Feature CSS is almost always :host { display: block }. If the look needed a page-level class, it went into the HTML.

What I would copy, and what I would not

Copy the order. Product language before generators. Domain, then feature, then UI component. One shared data kernel, not a shared domain. Infrastructure services when two facades share the same queries. The app as routes and an outlet. The shell as a feature. ESLint as the architecture.

Do not copy the in-memory store, except as a spike. Replace JiraClient and keep the facades. Do not invent symmetric API libraries you do not have. Do not use scope:shareable as a way to “reuse” another domain’s UI. Do not put logic in feature components, or effects that only copy signals.

A checklist you can run tomorrow

Write the product words on paper. Delete any that are not a reason to change. Run nx g nx-domainify:init. Generate the first domain with --directory=libs. For each remaining context, generate the domain, then the features, then the domain UI and util. Shared kits omit --domain and take --directory=ui or --directory=util with --skipPrefix. After each UI library, run @nx/angular:component --export.

Put the store and client in shared util, not in a shared domain. Keep injectQuery in domain infrastructure when more than one facade needs the same key. Put chrome in a shell feature. Leave apps/<name> as routes and <router-outlet />.

Run nx run-many -t lint. If a domain imports another domain, you cheated. Undo it.
